# 技术难点与解法

## 一、整体业务流程

用户从前端输入需求文档，可选上传参考图片，系统随后完成“需求对话 → 应用生成 → 构建预览 → 截图归档 → 代码托管 → 清理临时文件”的完整链路。
![应用生成工作流](images/generate-workflow.png)


项目的核心难点不在于单独调用大模型，而在于把模型输出、构建工具、容器预览、对象存储和数据库状态组织成一个可重试、可恢复、可追踪的流程。

## 二、用户登录与身份安全

* **多种登录方式统一成同一套登录态**：支持手机号验证码、邮箱验证码、微信扫码等入口，登录成功后统一生成用户身份信息，避免不同登录方式各自维护会话。
* **JWT 与 Redis 结合校验登录状态**：JWT 负责携带用户标识，Redis 保存登录用户和过期时间。网关先解析 JWT，再检查 Redis 中的登录态，解决“令牌格式有效但已经退出登录”的问题。
* **网关统一鉴权**：`AuthFilter` 在请求进入业务服务前完成白名单判断、令牌解析、登录状态检查，并将用户 ID、用户名和来源写入内部请求头，后续服务不需要重复解析登录信息。
* **令牌自动续期**：访问令牌接近过期时刷新 Redis 中的登录用户信息，降低用户在长时间生成应用过程中突然失效的概率。
* **敏感信息保护**：用户信息和登录令牌不能直接写入日志；密码、验证码、JWT 密钥、OSS 密钥和第三方代码仓库令牌应通过配置中心或环境变量注入，不能硬编码到前端和文档中。

## 三、需求对话与上下文管理

* **需求生成与代码生成分阶段处理**：前端先通过对话生成结构化需求文档，再将需求文档传递给应用生成页面，避免把用户的自然语言输入直接当作代码生成指令。
* **前端防重复提交**：生成期间通过 `isSending` 锁定发送操作，显示加载状态，并在请求结束后统一恢复，避免一次用户操作触发多个耗时工作流。
* **会话与应用绑定**：以 `appId` 作为 Spring AI 的 conversation ID，使需求、修改记录和代码生成上下文绑定到具体应用，而不是共享一个默认会话。
* **Redis + MySQL 双层记忆**：聊天记录先落数据库，Redis 保存最近消息并设置过期时间；读取时优先使用缓存，缓存未命中再从数据库恢复，兼顾访问速度和数据持久化。
* **源码不污染聊天记忆**：模型返回的 `FILE:` 代码内容不会完整写入后续对话上下文，只保留“应用已更新”或简短摘要，避免历史源码持续占用模型上下文窗口。

## 四、大模型生成的确定性约束

* **固定应用类型范围**：只允许生成 `Html`、`Vue3`、`Spring_Vue3` 三种类型，分别对应单页静态应用、前端工程和前后端工程，降低后续构建分支的复杂度。
* **系统提示词分层约束**：提示词同时规定模型角色、技术栈、目录结构、依赖版本、路由规则、数据存储方式和质量要求，避免模型只生成页面片段而不是完整工程。
* **固定输出协议**：模型第一行输出应用类型，随后按 `FILE: 相对路径` 和完整代码块输出文件。该协议便于 `AnalysisUtil` 解析目录结构，也能阻止模型输出额外解释影响文件提取。
* **完整文件而非差异片段**：要求模型输出所有文件的完整内容，避免只返回局部修改导致旧文件残留、目录结构不完整或前后端版本不一致。
* **参考图的多模态处理**：上传文件先保存到受控的 `user-reference/{appId}` 目录，只允许图片后缀进入视觉模型；参考图用于还原布局、配色和模块，不覆盖文字需求的功能约束。
* **图片搜索结果与模型解耦**：先由 MCP 图片搜索服务获取图片，再将可用图片映射为 `IMG_n` 提示交给模型，生成完成后替换为 OSS 地址；搜图失败时使用色块或 SVG，不让外部图片服务阻断主流程。

## 五、多智能体工作流编排

* **使用状态图管理复杂流程**：`MultiAgentWorkFlow` 将生成、构建、修复、截图和提交拆成独立节点，以状态字段传递 `appId`、代码路径、应用类型、错误信息和各节点结果。
* **条件路由替代深层嵌套代码**：每个节点只负责执行自己的动作，下一步由状态路由决定。例如生成成功进入预览，预览失败进入修复，截图或提交失败只重试对应节点。
* **节点级重试上限**：生成、截图和提交均限制最多执行次数，修复失败也受生成总次数约束，防止模型异常或外部服务故障造成无限循环。
* **失败原因分级**：构建阶段记录具体阶段，如 `npm_install`、`npm_build`、`mvn_package`、复制预览文件等，并区分“可以通过修改代码解决”和“需要处理环境或发布系统”的错误。
* **修复上下文裁剪**：修复节点把源码按“配置文件 > 入口文件 > 其余文件”的优先级挑出关键文件（最多 15 个），连同完整构建日志原文交给模型，既保留定位问题所需的信息，又避免把整份源码塞进一次请求导致超长和超时。
* **工作流状态覆盖策略**：状态字段采用 ReplaceStrategy，节点每次返回最新结果，避免重试时旧的成功标识、旧错误信息或旧文件列表污染当前分支。
* **并发隔离**：工作流以 `appId` 作为线程 ID 和会话 ID；应用代码、预览文件、截图文件也按 `appId` 分目录，防止不同用户的生成任务相互覆盖。

## 六、模型输出解析与本地文件安全

* **自然语言转目录结构**：模型输出需要解析成“相对路径 → 文件内容”的映射，再由文件写入工具创建目录和文件，这是从非结构化文本进入可执行工程的关键边界。
* **路径穿越防护**：写文件前将目标路径规范化，并验证目标仍位于当前应用目录下，拒绝 `../` 等越界路径，避免模型输出覆盖宿主机任意文件。
* **重生成清理旧目录**：同一个 `appId` 重新生成时先清理旧源码，防止上一次生成遗留的启动类、依赖目录或构建产物混入本次工程。
* **源码读取白名单**：提交和修复时只读取限定后缀的文本源码，并跳过 `node_modules`、`dist`、`target`、`.git` 等目录，控制内存占用和模型上下文长度。
* **文件大小控制**：读取源码时跳过过大的文件，避免单个模型生成文件拖垮提交、修复和后续网络传输。

## 七、三类应用的构建与预览

* **按应用类型选择构建策略**：
  * `Html`：直接复制 `index.html` 到预览目录。
  * `Vue3`：在项目目录执行 `npm install` 和 `npm run build`，再复制 `dist`。
  * `Spring_Vue3`：先构建 `frontend`，再执行后端 `mvn clean package -DskipTests`，复制前端产物和 JAR，并启动后端容器。
* **构建命令和工作目录必须严格匹配**：同一条命令在错误目录执行会导致依赖找不到、构建脚本不存在或生成物复制失败，因此每个阶段都明确绑定自己的工作目录。
* **外部命令错误可诊断**：命令执行工具需要保留原始标准输出和错误输出，并将其写入工作流状态，让修复智能体能够根据真实构建日志定位问题，而不是凭经验重写代码。
* **容器内执行与资源限制**：构建和启动用户生成代码属于高风险操作，需要限制容器权限、网络访问、CPU、内存、进程数和超时时间，避免生成代码影响门户服务或宿主机。
* **构建产物与源码分离**：源码位于 `user-code/{appId}`，预览产物位于 `user-preview/{appId}`，发布产物再复制到部署目录，减少构建目录、预览目录和发布目录相互污染。

## 八、跨容器目录挂载与 Nginx 预览

* **共享目录传递产物**：Portal 服务负责写入代码和预览文件，Preview 容器通过 Docker Compose 共享 `user-preview` 挂载目录读取静态资源，两个容器之间不依赖临时 HTTP 上传。
* **统一预览地址**：构建成功后根据 `nginxPre + appId` 生成访问地址，并将地址写回应用表，前端只需要消费数据库中的预览 URL。
* **前端路由兼容静态部署**：Vue 应用使用 Hash 路由，配合 Nginx 静态目录，避免刷新深层路由时被 Nginx 当作物理文件查找而返回 404。
* **前后端应用的网关前缀**：生成的 Spring Boot + Vue 应用要求前端请求使用 `/{appId}/api` 前缀，后端 Controller 统一使用 `/api`，由网关完成应用实例路由，防止多个用户应用的接口路径冲突。
* **后端 jar 端口按 appId 确定性分配**：`Spring_Vue3` 应用的后端不能都监听固定端口。系统用 `8001 + appId % 1999` 在 8001~9999 之间为每个应用算出一个固定端口，同一个 `appId` 端口不变，不同应用互不冲突，也便于按端口反查应用日志。
* **Nginx 动态注入 location 并热重载**：启动 jar 后调用 `update_nginx_location.sh`，用 awk 在预览 Nginx 的 `server` 块内为 `/{appId}/api/` 生成一段 `proxy_pass http://localhost:{port}/api/` 并写回 `/etc/nginx/nginx.conf`，随后 `nginx -s reload` 生效。重复构建时先删掉该 appId 的旧 location 再插入，避免配置层层叠加。
* **脚本的跨平台坑**：Windows 检出的 `.sh` 带 CRLF，容器里 bash 会把 `\r` 当命令名执行导致 `$'\r': command not found`。执行脚本前先 `sed -i 's/\r$//'`，仓库再通过 `.gitattributes` 把 `*.sh` 固定为 LF。
* **发布容器端口映射与冲突顺延**：发布时每个应用启动独立容器 `flashcode-userapp-{appId}`，宿主端口同样按 `generatePort(appId)` 算出并映射到容器内 80，容器内 jar 固定监听 8080、由容器内 Nginx 的 `location ~ ^/[0-9]+/api/` 静态转发；若宿主机端口已被占用则用 `nextDeployPort` 在 8001~9999 内顺延重试，避免端口冲突导致发布失败。
* **目录权限和一致性**：挂载目录需要保证 Portal、Preview、VS Code 和发布容器具有正确的读写权限；复制操作使用文件树复制而不是跨挂载点移动，避免不同磁盘或容器卷之间移动失败。

## 九、预览截图与对象存储

* **真实浏览器截图**：构建完成后使用 Selenium 驱动无头 Chrome 访问预览 URL，等待 `document.readyState=complete` 并额外等待页面资源渲染，再截取固定窗口尺寸的首页图片。
* **容器化浏览器兼容**：Chrome 在容器内需要 `--headless`、`--no-sandbox` 和 `--disable-dev-shm-usage` 等参数；镜像内预装 ChromeDriver，避免运行时访问外网下载驱动。
* **截图链路完整性**：截图文件先落本地，再转换成 `MultipartFile` 调用文件服务上传 OSS，上传成功后将在线地址写入应用表，只有数据库更新成功才将截图节点标记为完成。
* **失败可重试且资源可释放**：截图异常时关闭 WebDriver，记录失败信息并按节点次数重试，避免 Chrome 进程泄漏和同一应用积累大量临时截图。

## 十、代码托管与临时文件生命周期

* **先托管后清理**：截图成功后读取本地源码并推送到 Gitee 的应用目录，确认推送流程完成后才安排删除本地源码、参考图和本地截图。
* **延迟清理策略**：本地文件不是立即删除，而是通过定时任务延迟清理，给用户预览、在线编辑和故障排查留下时间窗口。
* **清理任务具备容错性**：删除失败只记录日志，不影响已经完成的应用状态；后续可通过定时补偿任务清理残留目录。
* **第三方服务失败不能丢失核心状态**：Gitee、OSS 等外部服务可能超时或限流，因此提交节点单独重试，数据库中的应用类型、预览地址和截图地址与代码托管状态分别维护。

## 十一、RAG、MCP 与图片资源生成

* **RAG 注入项目知识**：代码生成时通过向量库检索相关知识，将项目规范和历史经验作为上下文注入模型，降低模型生成不符合项目约束的代码概率。
* **MCP 图片搜索服务**：图片搜索被封装为独立的 MCP/服务能力，应用生成节点先查询资源，再通过占位符把资源信息传递给模型，避免在模型流式输出过程中临时调用工具导致输出不稳定。
* **图片 URL 脱敏与恢复**：需求进入模型前隐藏原始图片地址，模型只处理主体和 `IMG_n` 标识；代码生成完成后再恢复为可访问的 OSS 地址，减少模型篡改 URL 的概率。
* **外部依赖降级**：向量库或图片搜索暂时不可用时，应保留主流程的可用性，允许模型使用纯 CSS、SVG 或默认内容继续生成，并记录降级日志供排查。

## 十二、数据库与服务间数据一致性

* **应用状态分步持久化**：应用创建、应用类型、预览地址、截图地址和发布状态分别在对应流程节点更新，避免一次事务包住模型调用、构建和浏览器操作等长耗时任务。
* **幂等创建应用**：工作流开始时使用 `insertIfAbsent` 创建应用记录，并在用户身份确认后绑定所有者，支持重试时复用同一个 `appId`。
* **Feign 服务调用隔离**：Portal 通过 File API 调用文件服务上传截图，文件服务负责 OSS 适配，业务服务不直接耦合具体对象存储 SDK，便于更换存储实现。
* **统一返回和异常处理**：公共模块统一封装 `R`、结果码和业务异常，网关、Portal、文件服务对前端返回一致的错误结构，减少前端对不同服务异常格式的适配成本。

## 十三、前端交互与应用编辑流程

* **生成过程可视化**：聊天区域展示用户消息、附件预览、机器人加载状态和错误信息；生成成功后将需求文档和对话消息写入 `sessionStorage`，再跳转到应用详情页。
* **预览与对话分栏**：应用详情页同时承载预览面板和修改对话，用户可以基于当前应用继续提出修改要求，而不是每次从首页重新开始。
* **元素级修改**：前端通过元素选择器提交被选中的页面元素和新内容，后端读取当前源码并让模型生成完整更新结果，再重新进入构建预览流程。
* **高级编辑入口**：需要修改大量代码时，通过接口获取 VS Code Web 地址，直接编辑共享的 `user-code` 目录，完成后再触发高级编辑打包流程。
* **状态恢复**：应用详情接口同时返回应用数据和聊天历史，页面刷新后可以从后端恢复上下文，而不是只依赖浏览器内存。

## 十四、微服务部署与运维难点

* **模块化拆分**：后端按 Gateway、Portal、File、Image MCP 和 Common 模块拆分；公共模块承载安全、缓存、消息、领域对象和工具类，减少服务之间的重复实现。
* **配置中心管理环境差异**：Nacos 统一管理服务地址、模型参数、OSS、数据库和 Redis 配置，开发、测试、生产通过不同 Compose 和配置文件隔离。
* **Docker Compose 编排基础设施**：MySQL、Nacos、Redis、RabbitMQ、Milvus、MinIO、Preview、Web、VS Code、Prometheus 和 Grafana 通过 Compose 统一启动，并用 healthcheck 控制依赖启动顺序。
* **冷启动与健康检查**：Nacos、Milvus 等组件启动较慢，需要合理配置 `start_period`、重试次数和依赖条件，否则会出现服务实际正常但被 Compose 提前判定失败的问题。
* **监控生成耗时**：工作流按 `appId` 记录最近一次生成耗时，并通过 Micrometer 暴露计时器和 Gauge，便于在 Prometheus/Grafana 中观察成功率、耗时和异常集中阶段。
* **日志必须支持链路定位**：关键日志统一带 `appId`、用户、工作流节点、构建阶段和错误类型，避免面对异步构建、容器命令和浏览器截图失败时无法还原现场。

## 十五、主要工程约束

* 模型输出必须可解析，任何提示词调整都要同步验证三类应用的目录结构和构建命令。
* 用户生成代码属于不可信输入，所有路径、文件后缀、文件大小、命令参数和容器权限都必须经过限制。
* 长耗时节点必须有超时、重试上限、错误状态和资源释放逻辑，不能只依赖一次同步调用成功。
* 预览地址、截图地址、代码仓库地址和本地目录是不同生命周期的数据，不能用一个成功标识代替全部状态。
* 生产环境不得把 JWT 密钥、OSS 密钥、数据库密码、第三方令牌写入前端代码、源码仓库或公开文档。
